[slurm-env-var-not-found]
While trying to determine what resources are available, the SLURM
resource allocator expects to find the following environment variables:

    SLURM_NODELIST
    SLURM_TASKS_PER_NODE

However, it was unable to find the following environment variable:

    %s

This is a fatal error.
#
[slurm-env-var-bad-value]
While trying to determine what resources are available, the SLURM
resource allocator uses the following environment variables:

    SLURM_NODELIST       value: %s
    SLURM_TASKS_PER_NODE value: %s

However, an error was encountered when trying to parse the following variable:

    %s

This is a fatal error.
#
[tainted-envar]
While trying to determine what resources are available, the SLURM
resource allocator expects to find the following environment variable:

  Envar:  %s

The variable was found, but a length check has failed, indicating that
the envar is more than %d characters long. This indicates that the envar
may be tainted. We will therefore not print it out. However, if you check
and feel it is valid, then please adjust the length limit and try again.
#
[slurm-job-info-too-large]
The record Slurm returned for a job is larger than this DVM will read, so
the request that needed it cannot be served.

  Job:             %s
  Limit reached:   %lu bytes
  Nodes expected:  %d
  Allowed per node: %lu bytes

"scontrol show job --json" prints every socket and every core of every
allocated node, so a job's record grows with the total core count of the
nodes it holds, whether or not the job uses them. The limit above is
derived from the nodes this job was expected to hold and the
ras_slurm_job_info_bytes_per_node MCA parameter.

Raise that parameter if this cluster's nodes are larger than it assumes:

  --prtemca ras_slurm_job_info_bytes_per_node <bytes>

Setting it to 0 removes the limit entirely.
